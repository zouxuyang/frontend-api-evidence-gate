# 05 AI 驱动验收组件方案

## 结论

这个方向可行，推荐做成“规格驱动的验收执行器”，而不是让模型自由浏览页面后凭感觉打分。

标准链路是：

```text
验收规格文档
→ 规范化与校验
→ 变更影响分析
→ 选择需要重验的场景
→ 启动 Go API、Vue 页面和测试数据
→ 浏览器执行
→ 采集截图、DOM、请求和响应
→ 确定性规则判定
→ AI 语义判定
→ 标准化报告和证据归档
```

模型负责理解页面是否符合业务描述、信息层级是否合理、反馈文案是否合适；Playwright、schema 校验和规则引擎负责证明点击、输入、请求、响应、分页和布局是否符合要求。

## 1. 输入：验收规格文档

业务或开发人员提供一份结构化文档，建议使用 YAML，提交到代码仓库，例如：

```yaml
id: order-list
version: 3
route: /orders
owner: order-team

pages:
  - id: order-list
    route: /orders
    purpose: 查看和筛选订单
    viewports: [1440x900, 390x844]
    components:
      - id: order-table
        kind: table
        mustShow: [orderNo, status, amount, createdAt]
        detailOnly: [customerPhone, internalRemark]
      - id: edit-drawer
        kind: drawer
        trigger: 编辑

apis:
  - id: list-orders
    method: GET
    path: /api/orders
    query:
      page: integer
      pageSize: integer
      keyword: string?
    responseSchema: OrderPage
  - id: update-order
    method: PATCH
    path: /api/orders/:id
    requestSchema: UpdateOrder

scenarios:
  - id: search-and-page
    steps:
      - open: /orders
      - fill: { label: 搜索订单, value: ORD-001 }
      - click: 搜索
      - assertRequest:
          api: list-orders
          query: { page: 1, pageSize: 20, keyword: ORD-001 }
      - click: 下一页
      - assertRequest:
          api: list-orders
          query: { page: 2, pageSize: 20, keyword: ORD-001 }

  - id: edit-order
    steps:
      - open: /orders
      - click: 编辑
      - assertVisible: { role: dialog }
      - fill: { label: 备注, value: 需要尽快处理 }
      - click: 保存
      - assertRequest:
          api: update-order
          body: { remark: 需要尽快处理 }
      - assertVisible: 保存成功

quality:
  accessibility: critical
  screenshot: required
  maxRequestMs: 3000
  forbiddenConsoleErrors: true
```

文档必须区分：

- 页面和路由；
- 组件和控件；
- 用户动作；
- 预期请求；
- 请求体和响应 schema；
- 必须展示的字段与详情字段；
- 视觉、无障碍和性能要求；
- 必须执行和可以跳过的场景。

自然语言可以作为 `purpose` 和业务说明，但关键参数、按钮名称、字段、请求和断言必须结构化。

## 2. 规范化

执行器先把 YAML/Markdown 转成规范化 JSON，再运行 schema 校验。规范化过程需要：

- 字段排序；
- 默认值填充；
- 路由和 API 路径统一格式；
- label、testId、角色和 API id 建立引用；
- 将自然语言动作转换为有限动作集合；
- 为每个场景生成稳定的 `scenarioHash`。

模型可以帮助把自然语言初稿转换成结构化规格，但转换结果必须经过人工提交和 schema 校验，不能直接执行未校验的模型输出。

## 3. 验收执行

执行器为每个场景创建隔离运行上下文：

1. 启动或连接 Go 测试 API；
2. 准备固定版本的测试数据；
3. 启动 Vue preview；
4. 使用 Playwright 按步骤执行；
5. 监听 console、请求、响应、导航和 DOM；
6. 在关键步骤及最终状态截图；
7. 保存 Playwright trace 和 HAR；
8. 对请求和响应执行 schema 校验；
9. 对页面执行布局和无障碍规则；
10. 生成机器可读结果。

建议每个场景至少保存：

```text
artifacts/<run-id>/<scenario-id>/
├── result.json
├── screenshot.png
├── network.har
├── requests.json
├── responses.json
├── accessibility.json
└── trace.zip
```

## 4. 结果输出

统一输出 JSON，截图和 trace 通过相对路径引用：

```json
{
  "runId": "2026-10-17T12:00:00Z-abc123",
  "specId": "order-list",
  "specVersion": 3,
  "scenarioId": "edit-order",
  "status": "passed",
  "decision": "pass",
  "evidence": {
    "screenshot": "screenshot.png",
    "trace": "trace.zip",
    "requests": "requests.json",
    "responses": "responses.json"
  },
  "checks": [
    {
      "id": "update-order.request-body",
      "type": "api-contract",
      "status": "passed",
      "expected": { "remark": "需要尽快处理" },
      "actual": { "remark": "需要尽快处理" }
    }
  ],
  "aiReview": {
    "status": "passed",
    "confidence": 0.92,
    "findings": [],
    "evidenceRefs": ["screenshot.png", "requests.json"]
  }
}
```

`status` 表示执行状态：`passed`、`failed`、`blocked`、`skipped`。

`decision` 表示验收结论：`pass`、`fail`、`needs_review`。

执行失败和验收不通过必须区分：例如页面没启动是 `blocked`，接口字段错误是 `fail`。

## 5. AI 判定边界

### 规则引擎直接判定

以下问题不交给模型猜测：

- 元素是否存在；
- 按钮是否可点击；
- 输入值是否改变；
- 请求 URL、方法、query、body；
- 响应状态码和 schema；
- 分页参数；
- 是否出现成功或失败提示；
- 元素是否溢出、遮挡或超出视口；
- axe 严重级别问题；
- 控制台错误。

### 模型辅助判定

模型适合判断：

- 列表字段是否过多或主次不清；
- 页面信息层级是否符合验收说明；
- 弹窗或抽屉内容布局是否合理；
- 提示文案是否与用户动作一致；
- 截图中的视觉异常是否影响任务完成；
- 规格文档和实现之间是否存在语义偏差。

模型必须引用具体证据，不能只返回“看起来没问题”。

### 结论合并

建议使用以下规则：

```text
确定性规则失败       → fail
执行环境或数据不可用 → blocked
规则全部通过且 AI 通过 → pass
规则通过但 AI 低置信或发现语义问题 → needs_review
```

模型不能把确定性规则失败改成通过，也不能把缺失证据判定为通过。

## 6. 评估这个方案

### 优点

- 验收输入、过程和输出都可版本化；
- 能复用同一份规格文档生成测试和报告；
- 可以只重跑受影响页面，减少重复验证；
- 截图、请求和响应能作为可审查证据；
- AI 适合补足人工判断中的信息层级和语义检查。

### 风险

- 自然语言规格不完整时，自动化只能验证已声明内容；
- 测试数据、权限和外部接口变化会造成假失败；
- 视觉模型可能误判，需要规则和人工复核兜底；
- 如果每次都让模型自由探索，结果不可重复、成本高；
- 截图相同不代表请求和数据逻辑没有变化。

### 建议结论

先做“规格驱动 + 确定性执行 + AI 复核”的 MVP，不要一开始做完全自主的 AI 验收员。第一版只支持结构化动作、关键请求断言、截图、HAR、JSON 报告和受控 AI 复核；稳定后再扩展自然语言理解和视觉判断。
