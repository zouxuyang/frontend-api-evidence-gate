# 01 总体方案

## 1. 目标

让 Codex 生成或修改 Go+Vue 功能后，能够通过统一的自动化和人工检查证明：页面可操作、数据可传递、接口符合约定、布局可用、列表和反馈行为正确。

## 2. 验收对象

每个功能以“用户场景”作为验收单位，而不是只以文件或组件作为验收单位。例如：

```text
进入订单列表
→ 显示加载状态
→ 使用后端分页
→ 输入搜索条件
→ 点击搜索并发送正确请求
→ 打开详情抽屉
→ 打开编辑表单
→ 修改字段并提交
→ 验证请求体
→ 验证成功提示和列表刷新
→ 验证失败提示和数据保留
```

## 3. 四类证据

### 代码证据

- Go 单元测试和静态检查通过；
- Vue 类型检查、Lint、组件测试通过；
- OpenAPI 或 schema 与生成类型一致。

### 浏览器证据

- Playwright 可以完成关键用户流程；
- 关键请求的 URL、方法、参数和请求体正确；
- 弹窗、抽屉、提示、分页和表单操作有明确结果。

### 视觉证据

- 关键 viewport 下无明显换行、遮挡、溢出；
- 表格列有明确主次；
- 空数据、长文本、错误和加载状态布局可用。

### 过程证据

- Codex 报告实际执行过的命令；
- CI 保存测试报告、截图和失败 trace；
- 未执行或阻塞的检查被明确标出。

## 4. 责任边界

- Codex：读取规范、实现代码、执行检查、修复失败、汇报证据；
- 开发者：提供可启动环境、测试账号和业务规则；
- CI：执行不可绕过的门禁；
- 产品或业务人员：判断字段价值、信息层级和流程是否符合业务目标。

## 5. 不合格判定

以下任一情况都不能标记为验收通过：

- 只通过编译，没有浏览器流程证据；
- 只看截图，没有验证真实请求；
- 测试只使用三条固定数据，没有空数据、长文本和分页边界；
- 请求能发出，但字段、枚举或分页协议不符合接口定义；
- 有按钮但没有成功、失败或加载反馈；
- 检查失败后绕过门禁或只在报告中写“预计通过”。
